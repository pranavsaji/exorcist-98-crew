Found only by installing (not in the Manifest reference):

- **N-001** The gateway refuses an app with `crons` and no `permissions.cron: true`. Fixed in `app.json` and in `shared/manifest.ts`, with a test.
- **N-002** The gateway probes `/health` without a signature. The backend answered 401 until `/health` was moved before the signature check (fixed in `backend/src/server.ts`, with a test). The gateway then listed the backend as reachable.
- **N-003** Enabling a third-party app is refused until it is trusted (`agent.apps_trusted`). This machine's config now trusts only `exorcist-98-crew`.
- **N-004** The backend reads its scanner path once at start. Adding `cliPath` to `~/.exorcist-98-crew/config.json` needs a disable and enable to take effect.


Accessibility inside Crew: axe on the full dashboard page reports 4 `label-content-name-mismatch` violations. All four are Crew's own top-bar buttons (Command Bar, resource health, update pill, notifications), none are in this app's page.
- **N-005** App notifications need three things the docs do not list: exchange the app secret for a token (`POST /api/apps/<name>/token` with `X-App-Secret`), send that token as the `mc_token_<port>` cookie (the gateway ignores `Authorization: Bearer` and answered `403 Token required`), and declare the channel under `notifications.channels` in `app.json`. Fixed in `backend/src/notify.ts`, with tests; seen working in Crew 0.12.2.
- **N-006** A trust grant (`agent.apps_trusted`) made before installing is refused at install ("execution trust predates repository binding"). Install first, then trust, then enable.
- **N-007** Fixed. The scheduled patrol was watched on a real clock on the main gateway (Crew 0.13.0): with `patrolTime` set to 21:10 in the app's `data/config.json`, it ran at 21:10:00.005 local time, found the two problems in a defanged sample folder and the Crew notification arrived at 21:10:00.19. `patrolTime` (`HH:MM`, `H` or `off`) is now read from the config file, because Crew does not pass custom environment variables to app backends; the setting was then removed, so the patrol is back at 02:00.
- **N-008** On the main gateway the agent cron fired at 02:57 and failed because the Sentry agent was not registered at the time ("agent definition ... is missing"); an update registered it. Crew applies a manifest's `enabled: false` only when it creates the job, so an existing job stays enabled after an update. Paused by hand; new installs get it paused.
- **N-009** (Crew 0.13.0, signed in.) The Sentry agent answers in chat and the agent cron runs, but neither can read the patrol: the agent has no gateway token (C-007), so both replies say they cannot reach the results and point to the page. The agent's prompt still told it to `POST /patrol`; it now says the backend patrols and notifies by itself, and that it must never guess results (test in `tests/manifest.test.ts`). The cron adds nothing the backend notification does not already give. It stays paused; removing it is a product decision, not made here.
- **N-010** Crew's own scaffold (`kirocrew app init --backend --ui --cron`) was installed and enabled as a sample app on the same gateway, then disabled. Its page rendered, and it confirms three findings above: `permissions.cron: true` with crons (N-001), a React default export as the page (C-002), and `PORT` for the backend (C-003). Its `ui` needs `npm install --legacy-peer-deps`, because npm 7+ installs the `@kirocrew/app-sdk` peer dependency, which is not on npm (404). The sample's own backend did not answer `/health` through the proxy (404); this app's did.
- **N-013** The scanner's EX-003 "Encoded payload" rule fires on the Shield's own SHA-256 hashes in `.exorcist/pins.json` (3 high findings for one pinned tool, seen in Crew 0.13.0). The rug-pull watch drops EX-003 on that one file only; all other rules still apply there.
- **N-014** Tool and server names in a pin file come from the MCP server, so they are kept out of finding titles (which reach the agent and notifications) and shown only in the quoted text on the page. PBT-CRW-06 checks the title is fixed and the agent view has no quoted text.
- **N-011** (Crew 0.13.0, signed in.) The Sentry agent can now read the patrol. `mcp/patrol_status.py` is a read-only stdio MCP server (Python standard library only) that reads the backend's `state.json` and returns levels, counts, failed scans and findings (rule, severity, title, file, line), never quoted text or fixes; file names are cleaned and the result is labelled as data. Crew registers an app's server as `<app>:<server>`, so the agent's tool ref must be `@exorcist-98-crew:exorcist-patrol` (a plain `@exorcist-patrol` was logged as "not found" and never mounted). Crew rewrites the relative `.py` launcher to an absolute path and its own Python. Each call needs the user's approval: a non-interactive `kirocrew chat -m` declines it automatically; in an interactive chat, approving once returned the Haunted Repo (critical, 17/21/2, 25 of 40 listed, 15 omitted), and none of the 26 quoted spans appeared in the reply (seen). The cron, still paused, now asks for the same tool; an unattended cron run would hit the same approval gate.
- **N-012** The agent cron now runs unattended. The Sentry agent's spec pre-approves exactly one tool, `@exorcist-98-crew:exorcist-patrol/patrol_status` (read-only), in `allowedTools`; Crew 0.13.0 kept it when materialising the agent (seen), and every other tool still asks. A triggered run (`kirocrew cron trigger`) finished with status success, no approval prompt and no denial in its trace, reported the Haunted Repo correctly (critical, 17/21/2, 25 of 40 listed), and contained none of the 26 quoted spans (seen). Crew's `--approval-mode auto` was not used, because it would approve every tool the agent can reach. The cron is now enabled at 02:15, after the 02:00 patrol, so it reports that night's results.
- **N-015** Second real-clock check of the nightly timer, outside Crew: the built backend with `EXORCIST_PATROL_HOUR=22`, started at 21:02, patrolled at 22:00:00.126 local and stored the Haunted Repo's 40 findings. Together with N-007 (session B, inside Crew at 21:10), the timer has fired on a real clock twice.
- **C-018** Fixed, as a confirm-first action (not one-click). "Move file to vault..." and "Restore..." on the page call the main repo's Quarantine Vault (`exorcist vault quarantine-file` / `restore`). The backend accepts them only when the gateway's signed principal (`backend.signedPrincipal`, `X-KiroCrew-Principal`) says `owner-session`, the request carries `x-exorcist-action` and a confirm word, and the file is named by the last patrol, is a regular file inside the folder (no symlinks on the way) and is not under `.exorcist/`. Scans skip `.exorcist/vault`. Seen in Crew 0.13.0 (2026-11-20): a `?token=` caller got 403; the owner moved and restored a file from the page, same sha256. MCP servers are not quarantined from the page (their names come from scanned text; the Shield already hides changed tools). **Residual risk:** any other app you trust in Crew runs its page code in the same dashboard, as you, so it could call this too; trust only apps you have reviewed. Gateways without the principal header (Crew 0.12.2) refuse every move.
- **N-016** The real nightly patrol on the main gateway ran at 02:00:00 local on 2026-11-20 (`lastPatrolAt` 10:00:00.002Z), before the Mac restarted at about 05:30 and stopped the gateway. The gateway does not start by itself after a restart unless `kirocrew service install` is used. Fixed on this Mac (2026-11-20 10:06): the gateway now runs as a launchd service (`RunAtLoad`, `KeepAlive`); undo with `kirocrew service uninstall`.
- **N-017** `signedPrincipal` is read from Crew 0.13.0's source (`apps/proxy_auth.py`), not from the docs. `shared/principal.ts` was checked against headers made by Crew's own `sign_proxy_principal_claim` (`tests/principal-vectors.json`, a test secret).
- **N-017** A full real night on the main gateway (Crew 0.13.0, 2026-11-20): the backend patrolled at 02:00 (N-016), and the agent cron ran on schedule at 02:15:00 (job `1e89f00f`, trigger `scheduled`) and finished with status success after 380 s, with no approval prompt or denial. Its report named the 02:00 patrol, the folder and its level, and contained none of the 26 quoted spans (seen in `~/.kiro/crew/cron-history/1e89f00f.jsonl`).
